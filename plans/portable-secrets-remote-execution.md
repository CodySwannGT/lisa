# Portable secrets and remote execution

## Context

Provide a host project with the secrets it needs **wherever it runs** — Codex Cloud, GitHub
Actions, a local desktop, and later Claude Code web / Cursor remote — and let a project dispatch
its own work to a remote surface without the operator's laptop being the execution substrate.

A credentials manager is the **preferred and best-supported** path. It is never required.

The design is promoted from a working implementation proven in production on 2026-08-01:
`gunnertech/frontend#165` (repository-owned Codex Cloud Bitwarden bootstrap) plus the end-to-end
publisher run that carried a real post from dispatch through merge and deployment. Every rule
below that carries a "proven" note came out of a real failure in that stack, not from theory.

Lisa already has `lisa-secrets-access` (added 2026-07-28, PR #2127). It is the right shape and the
wrong scope: it models providers only, has **zero callers and zero tests**, and its absolute
"never write to disk" rule makes the Codex Cloud case inexpressible.

## Source-of-truth note

Edits go to **`plugins/src/base/`**. The `plugins/lisa/`, `plugins/lisa-cursor/`,
`plugins/lisa-agy/`, and `plugins/lisa-copilot/` trees are regenerated by `bun run build:plugins`
and committed alongside source changes. Any template/source edit also requires
`bun run build:upstream-evidence-manifest` **in the same commit** or CI fails on a stale manifest.

## The two axes

Lisa today models one axis and needs two.

| Axis | Values | What it determines |
| --- | --- | --- |
| **Provider** | bitwarden, 1password, aws, doppler, vault, env | Where secrets live |
| **Surface** | local, codex-cloud, github-actions (+ future) | How they arrive at the running code |

`lisa-secrets-access` models the provider axis only. Every lesson from the proven implementation
lives on the surface axis, which is why none of it can be expressed today.

## Part A — Secrets standard

### A.1 Resolution ladder

One rule, one order. Only the middle rung varies by surface.

```
env  →  materialized file (surfaces that have one)  →  live provider read
```

- **local** — env, then live provider read (bootstrap from keychain)
- **codex-cloud** — env, then the materialized file. A container cannot do a live read before the
  agent phase; that is the entire reason materialization exists.
- **github-actions** — env (injected), then live read with the repo-secret bootstrap

### A.2 Surface-conditional disk writes

`lisa-secrets-access` Rule 3 today is absolute: *"Never write a resolved value to disk, including
'temporary' files."*

This becomes **surface-conditional**:

- Forbidden on surfaces that can read through live (local, github-actions).
- Required, with a fixed shape, on surfaces that cannot (codex-cloud).

A deliberate relaxation, not an oversight. It is the largest single reconciliation in this plan and
must be documented as such in the skill so a future reader does not "restore" the absolute rule.

### A.3 Materialization contract

```
${XDG_CONFIG_HOME:-$HOME/.config}/$LISA_SECRETS_NAMESPACE/     # dir 0700
├── secrets.env         # 0600, values, shell-quoted, never printed or parsed by the note reader
└── secret-notes.json   # 0600, notes only, no values, schemaVersion pinned
```

- Namespace validated as **one safe path segment** so config cannot redirect writes.
- Materialized **atomically from one provider response**, so values and notes are the same revision.
- Temp files created beside their destination so the final rename is same-filesystem atomic.
- Retrieval stays in a shell wrapper; parsing and filtering live in a separate program, so all of
  it is testable with synthetic data and no secret access.

### A.4 Exposure boundary

The provider's own scoping is the default allowlist — the machine account's project grants *are*
the permitted set. Optional controls may only **narrow**: a project-ID filter and an exact-name
exclusion list.

**Duplicate exact-name keys are a hard failure.** Choosing one would make credential use depend on
response order. Lisa's current `Map.set` silently violates this (last-wins).

Keys must be exact environment-variable names. No inference, no fuzzy matching, no case folding.

### A.5 Notes — two rules, not one

Currently conflated upstream. They separate cleanly:

- **Rule A — the note must exist and be well-formed.** Universal: every secret, every provider,
  every surface. Enforced **statically** by `doctor` / `verify`. Nothing to do with agents.
- **Rule B — an agent must read the note before first use.** Runtime, and only in lanes where a
  consumer has *latitude*. An agent could do anything with a write-scoped token and the note is
  what bounds it. A reviewed workflow step resolving one credential by exact name has no latitude,
  so gating it is ceremony that can only fail-closed and never inform.

Notes explain purpose, scope, owner, rotation, cautions. They never contain values, and they cannot
override system/developer instructions, `AGENTS.md`, an invoked skill, permission boundaries, or
secret-handling rules.

Empty note → **infer from the name, mark it inferred, and report the gap.** Never infer silently,
and an inferred mapping must never authorise a write.

### A.6 Rotating credentials

The defining property is not "OAuth" — it is that **using the credential can invalidate the stored
copy**. Consumable credentials. That generalizes past the two known cases to STS sessions,
single-use enrollment tokens, and anything issuer-rotated.

The danger observed in production was never rotation itself; it was **rotation with no proven write
path**. A reporting script was wired into a nightly job where the provider CLI was not installed;
the first scheduled run would have rotated the vendor token, failed to persist the replacement, and
broken every downstream consumer.

1. **Declared, never inferred.** `secrets.rotating: [...]` in config — not derived from the note,
   because the note lives provider-side and a read-only account cannot correct a wrong one. Default
   empty; most projects declare none.
2. **A distinct verb.** A plain `get` handing a consumable token to code with no write-back path
   *is* the failure mode. Reading a rotating credential is a different operation.
3. **Three obligations, all proven before the irreversible use:**
   - **Write-scope preflight** — a no-op re-write of the current value, generalized per provider.
     Highest-value item in this section: it converts a silent multi-day breakage into a startup
     error.
   - **Exclusive lease** (below).
   - **Persist-on-exit** — write back on failure paths too, not only success.
4. **The read chokepoint stays read-only.** Do not relax "never writes." Add a *sibling* writer
   with explicit authority that only declared-rotating credentials may route through.
5. **The lease is advisory, and we say so.** True cross-surface mutual exclusion is unsolvable with
   per-surface primitives — a GH Actions concurrency group and a local lockfile do not know about
   each other. The one substrate every surface shares is **the provider**, so the lease lives
   there: holder, surface, timestamp, with expiry so a crashed holder self-heals. Documented as
   advisory, not as a mutex.
6. **`verify` catches the dangerous configuration** — a declared-rotating secret reachable from a
   lane with no proven write path. That is the failure above, detected at config time instead of on
   the first scheduled run.

**Decided:** split read and write machine accounts by default where the provider supports it. The
single read/write account tradeoff (a leaked token means confidentiality is already gone; write
adds sabotage rather than disclosure; a second account is a paid unit) is documented as available,
not baked in.

### A.7 Not forcing a manager

A project with no `secrets` block still works — the `env` provider is the escape hatch and the
environment is the provider. `doctor` **warns**, never blocks, and the warning names the preferred
path and what it buys.

### A.8 Provider coverage

Implemented: **bitwarden**, **doppler**, **env** (already true today). Documented in the dispatch
table with an actionable "add one here" error: 1password, aws, vault. Do not pretend to support
what is not implemented.

## Part B — Remote environment setup

### B.1 The setup script

Lisa generates one repo-owned setup script. Three phases, in order:

1. **Bootstrap and materialize secrets.** Install pinned + checksummed provider CLI, pull the
   scoped project, write `secrets.env` and `secret-notes.json`. Identical for every project.
2. **Satisfy the declared toolchain** (B.2).
3. **Run the project's own hook if present** — an optional `setup.local.sh` the project owns, for
   anything declarative cannot express. Without this, projects fork Lisa's script.

**Setup and maintenance are the same script.** Codex Cloud runs setup on a fresh container and
maintenance when it resumes a cached one. Every step is idempotent and version-aware, so re-running
is correct in both cases. The remote environment's config fields stay two one-line calls into the
repository — nothing pasted into a vendor UI.

### B.2 Toolchain manifest — two entry kinds

Remote environments arrive with a base image that already provides much of what a project needs.

- **`require`** — assert present (optionally at a minimum or exact version), fail setup with a
  clear message if missing. For everything the base image already provides.
- **`install`** — provision it, pinned and checksummed. Only for what genuinely is not there.

Both patterns exist in the proven implementation: the bootstrap scripts use `python3`, `curl`,
`unzip`, `sha256sum`, and `install` without installing them, while the auth-health script runs a
`command -v` loop that fails clearly rather than provisioning.

- **The base image is not a contract.** A project quietly depending on preinstalled `jq` should
  break loudly at setup when the vendor changes the image, not mysteriously mid-task weeks later.
  `require` converts an implicit assumption into an explicit check.
- **Detect first, install second.** Check the installed version, skip if it matches the pin,
  reinstall only if the pin changed. This is what makes setup == maintenance, and it is the cheap
  path on cache resume.
- **Version-assert, not just presence.** A base-image bump that moves off a supported Node or
  Python must be caught.
- **Prefer what is there.** A second Node beside the image's creates PATH ambiguity and wastes
  container time.
- **Pin and checksum together, in one reviewed commit.** A version bump that does not move the
  checksum must fail before installation.

Expected shape for most projects: a short `require` list, an empty or near-empty `install` list,
and the provider CLI as the only thing Lisa always provisions.

### B.3 Tooling is never derived from secret notes

Rejected deliberately:

- Most tooling has no credential (`jq`, ripgrep, Playwright browsers, a linter), so notes could
  only cover a subset and a second mechanism would be needed anyway.
- Most credentials imply no tool — a webhook is curl'd, a REST key needs no CLI.
- The mapping is guesswork (which CLI, what version, pinned how) and is exactly the inference the
  secrets contract already forbids from authorising anything.
- It makes prose load-bearing: a note lives provider-side, is editable outside a PR, and is
  unfixable by a read-only account.
- It is a supply-chain path — provider write access would become arbitrary install access.

**Notes are an assertion target instead.** At verify time: a tool declaring a credential that is
not materialized is an **error**; a credential materialized with no declared consumer is a **warn**
(possible orphan). The arrow points the safe way — the repository declares intent, the provider is
checked against it.

### B.4 Provisioning tiers

1. **API** — provision programmatically.
2. **Computer-use / browser** — drive the vendor console.
3. **Emit** — generate exact config for a human to paste.

### B.5 Verification is tier-independent

**Whatever tier provisioned it, the same read-back proves it.** Trust comes from the verify, not
the mechanism.

The read-back asserts, without printing a value: namespace and directory mode, both file modes,
note readability for each declared credential, presence and non-emptiness of each required
variable, explicit exclusion of anything that must not be present, each declared tool at its pinned
version, and a clean checkout.

**Never verify against vendor UI state.** On 2026-08-01 the Codex environments table reported zero
tasks for an environment that had completed one, because task records carried a null environment
identifier and the `--env` filter was correspondingly unreliable. Reconcile through durable
identifiers only.

### B.6 Preconditions at registration

Checked when setup runs, not at 3am: the environment exists, is bound to *this* repository, has its
bootstrap, and the repo has Lisa applied so skills are present in the default checkout. Fail naming
what is missing.

## Part C — `executionEnv` dispatch

### C.1 The parameter

```
/lisa:implement executionEnv=codex-cloud SE-45434
```

Values today: `local` (default when omitted) and `codex-cloud`. Named `executionEnv` rather than
`env` because Lisa already uses "environment" for deploy stages throughout (deploy chain,
`status:on-dev`, env-aware done statuses).

A skill that does not support `executionEnv` must **reject it explicitly**, never ignore it.

### C.2 Routing only

`executionEnv` changes **where** work happens and nothing about **what** happens. The remote runs
the identical skill from the identical repository. Any behavioral difference belongs in the skill
as an explicit branch, never in the dispatch.

The invocation stays thin — `$lisa-implement SE-45434` — with all durable behavior in the
repo-local skill, so interactive, scheduled, and recovery runs execute one contract.

### C.3 Fire-and-record

Empirically confirmed: `codex cloud exec` **submits and returns**. Measured at **4s** and **3s** in
two production runs, with total dispatcher jobs of 14s and 15s. The Cloud task opened its PR nearly
six minutes after GitHub had finished and stopped billing.

1. Verify preconditions (B.6). Fail naming the setup command; never dispatch and hope.
2. `codex cloud exec --env <id> --branch <branch> [-c model=...] '<thin invocation>'`
3. Write task ID, ticket, branch, timestamp to `.lisa/` durable state.
4. Print the task URL and **exit**. No polling, no watcher.

The laptop is a launcher, not the execution substrate. Closing it is harmless.

### C.4 Model and attempts

`codex cloud exec` has **no `-m/--model` flag** but accepts `-c/--config`; the CLI's own help
example is `-c model="o3"`. **`--attempts <N>`** (best-of-N, default 1) is a direct multiplier on
Cloud consumption and should be explicit. `--branch` defaults to the *current* branch, so it must
always be passed explicitly.

Model is vendor-specific while `executionEnv` is routing, so it is scoped under the surface:

```json
"executionEnv": "codex-cloud",
"codexCloud": { "model": "...", "attempts": 1 }
```

Resolution: per-invocation override → project config → environment default.

**Do not invent an abstract tier** (`fast` / `deep`) mapped per vendor; that produces confidently
wrong mappings. A raw string scoped to the surface that owns it is honest.

Model applies to work-doing invocations only. Auth-refresh and health-check paths never need it.

### C.5 The ticket body is untrusted input

This is an agent dispatching an agent, where the ticket body *is* the instruction and is editable
by anyone with tracker access. It must not expand the remote run's authority, select tools, request
secrets, or weaken a gate. The boundary is fixed by the skill and the environment, stated
independently of what the ticket says.

### C.6 Scope

`lisa-implement` first, proven end to end on one real ticket through to a merged PR, before
extending to `plan`, `research`, `verify`, `intake`.

## Part D — Scheduler

### D.1 Registration is the seam

Lisa already has `lisa-setup-automations`, `lisa-automation-status`, `lisa-tear-down-automations`,
and an Automation Runbook Contract stating that membership is *registration, not skill-existence*.
This plugs into that machinery rather than growing a parallel one.

```json
"automations": {
  "intake": {
    "scheduler": "github-actions",
    "schedule": "17 * * * *",
    "executionEnv": "codex-cloud",
    "enabled": false
  }
}
```

`scheduler` is the pluggable seam — the same declaration generates a GH Actions workflow today and
can register a Claude routine later without touching the loop. Config is the source of truth; the
workflow is generated from it.

### D.2 GitHub Actions as the default clock

Once `executionEnv=codex-cloud` exists the scheduled job is a thin dispatcher; the heavy lifting is
on Codex's machines. The clock wants to be cheap, boring, and reliably always-on, not powerful.

GH Actions is already in every host project, already has the secrets lane, and has native cron,
concurrency groups, retries, manual dispatch, and an audit trail.

**Cost:** billed per minute, rounded up, so a 14-second job costs one minute — roughly $0.008 per
dispatch on a private repo, free on a public one; nightly for a year is about $3. The rounding is
*per workflow run*, so batching N dispatches into one run is far cheaper than N triggers. The real
cost is the Codex Cloud task consuming subscription quota; GH Actions is a rounding error beside it.

Rejected: **Codex Automations** (run locally off `~/.codex/automations/` — the same laptop problem
in different clothing). Available later: **Claude routines** (cloud-hosted and the agent is the
runtime, but a second vendor and the schedule is not reviewable in a PR).

### D.3 Generated workflow shape

- `workflow_dispatch` always; `schedule` present only when `enabled: true`
- **non-cancelling concurrency group** — cancel-in-progress could kill a dispatch after Codex
  accepted the task but before the task ID was recorded, orphaning irreversible work
- `permissions: contents: read`
- assert bootstrap present → install pinned+checksummed provider CLI → restore rotating dispatcher
  credential → install pinned agent CLI → dispatch → persist rotation and wipe, `if: always()`

The dispatcher authenticates to Codex with a credential that rotates on use, so the first artifact
this plan produces already exercises the rotating-credential path in A.6. Not hypothetical.

### D.4 Registered disabled

A recurring trigger goes live only after the exact production path has been proven once for one
real item. Setup writes the workflow with manual dispatch only; enabling adds the cron.

GitHub **auto-disables scheduled workflows after 60 days of repository inactivity** — a real trap
for an unattended factory, since a quiet repo silently stops running its loops.
`lisa-automation-status` must detect a stopped clock, the way an auth-health loop detects a dead
credential.

**Decided:** `automation-status` reports on the clock only. Reconciling dispatched Cloud tasks is
adjacent to merge/convergence, which is explicitly out of scope for this plan.

### D.5 Runbook and outcomes

The contract requires a checked-in runbook per registered loop and every run to end in exactly one
of `nothing-needed | candidate-proposed | change-proved | approval-requested | recovery-required |
policy-obsolete`. For a dispatch loop: empty queue → `nothing-needed`; item dispatched →
`candidate-proposed`; broken environment or dead credential → `recovery-required`.

Registration produces three artifacts: the config entry, the generated workflow, and the runbook.

**Decided:** scheduled intake **batches** — one run dispatches N eligible items rather than one
item per tick. Per-run billing rounding makes it strictly cheaper, and the contract change to
intake is small.

## Part E — Wiring and tests

**This is what makes the rest real, and it is the larger half.**

`lisa-secrets-access` today has **zero callers and zero tests**. Its own SKILL.md says every skill
needing an API key MUST route through it; none do. It is referenced only by its own files,
`CHANGELOG.md`, and a path listing in `upstream-evidence-manifest.ts`.

1. **Route the callers.** Find every skill and script resolving credentials directly and move them
   behind the chokepoint. The single-store rule is unenforceable until this is done.
2. **Tests.** Parsing, filtering, boundary, duplicate-failure, note separation, missing-note
   refusal, ladder precedence per surface, rotating-credential preflight. The retrieval/parsing
   split exists precisely so this is testable without granting the test process secret access.
3. **Doctor checks**, currently documented but unwired: every `require` name resolves; every key
   matches `^[A-Z][A-Z0-9_]*$`; no secret has an empty note; **no secret is readable from two
   stores** (highest value — two live credentials, one untracked).
4. **Config schema** for `secrets`, `remoteEnv`, and `automations`, so a malformed block fails at
   `doctor` rather than at use.

## Open unknowns

1. ~~**Does Codex Cloud expose a provisioning API?**~~ **Answered 2026-08-01: no.** `codex cloud`
   exposes only `exec | status | list | apply | diff`. B.4 tier 1 is unavailable for this surface, so
   setup starts at the console/emit tiers and says so rather than claiming an API that does not exist.
2. **Does Codex Cloud cap concurrent tasks per account?** Still open. Bounds useful fan-out; a quota
   question, not a dollar question. Needs a live account to answer.
3. **Does `-c model=` propagate into the Cloud task,** or does the environment's own setting win?
   Still open. The flag documents itself as overriding the *dispatching* machine's
   `~/.codex/config.toml`. One real dispatch settles it; deferred rather than burn quota probing.

Neither remaining unknown blocks anything shipped: both concern tuning a dispatch, not whether one
works.
