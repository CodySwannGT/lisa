3:description: This skill should be used when updating local Lisa projects in batches. It rolls out canary-first - it reads the project list, each project's target branch and the one designated canary host from the .lisa.workspaces.json workspace config, upgrades the canary first and waits (bounded) for its update PR's required checks, and only if they pass updates the remaining hosts; a failing or timed-out canary halts the rollout with no other host touched. For each host it works in a dedicated git worktree based off that target branch, runs the package manager update for @codyswann/lisa, migrates legacy CI workflows, checks for upstream changes, commits, pushes, and opens a PR targeting the configured branch with auto-merge enabled, auto-fixing any blockers to mergeability (upstreaming fixes when needed). As the final step, Lisa upgrades itself, unless the canary halted the rollout. It always ends with a report that includes a canary section.
10:The rollout is **canary-first** (CodySwannGT/lisa#4604): one designated canary host is upgraded first, and the rest are touched only once the canary's update PR passes its required checks. A bad Lisa release then breaks one host, not every host. See [Rollout Order](#rollout-order-canary-first) for the phases and [Report](#report) for what the run must print.
14:1. Read @.lisa.workspaces.json to get the list of host projects, each project's target branch, and the canary. The file is a JSON map of project path → target branch. Each value is either the legacy branch string (e.g. `"~/workspace/foo/backend": "staging"`) or the object form `{ "branch": "<target branch>", "canary": true }` (`canary` is optional and boolean; `{ "branch": "main" }` is also valid). The branch is the one that project's update PR must target. Branches vary per project (`main`, `staging`, `dev`, …) — never assume `main`. **Exactly one** entry must set `"canary": true`. Do not parse the file by hand — run the plan script from the Lisa repo root:
18:   # prints {"canary":{"path":…,"branch":…},"rest":[{"path":…,"branch":…},…]}
21:   Use its `canary` and `rest` phases (and each entry's `branch`) for every step below. If it exits non-zero — no canary, two or more canaries, or a malformed entry — **stop before touching any host**, show the human its stderr message, and ask them to designate exactly one canary by changing that host's value to the object form, e.g. `"<host path>": { "branch": "<target branch>", "canary": true }`. Never pick a canary yourself, and never fall back to updating every host at once. Then run steps 2–17 only in the order given by Rollout Order below — never across all hosts at once.
23:3. Do **all** work for a host project inside a dedicated git worktree based off that project's configured target branch — never modify the project's primary checkout. Create it with the update branch in one step, e.g. `git worktree add <worktree-path>/<project>-lisa-update-YYYY-MM-DD -b chore/lisa-update-YYYY-MM-DD origin/<target-branch>`, where `<target-branch>` is that host's `branch` from step 1's plan. This keeps the project's main working tree untouched, isolates each project's changes, and lets the parallel subagents operate without colliding. Clean up the worktree (`git worktree remove`) after the PR is opened and the branch is pushed — for the canary, only after its push timing has been recorded (Rollout Order, phase 3).
83:17. As the final step, have Lisa upgrade itself: run this same update flow against the Lisa monorepo (the current working directory) — bump `@codyswann/lisa` to latest where Lisa consumes its own templates, apply templates, and commit/push/PR a self-update branch with auto-merge enabled, following the same worktree (rule 3), auto-merge (step 14), and blocker-fixing (step 16) rules. Skip this step if the Lisa repo has no pending self-update changes after running the flow, **and always skip it when the canary halted the rollout** (see Rollout Order).
85:## Rollout Order (canary first)
90:2. **Canary.** Run steps 2–15 for the plan's `canary` host only, exactly as for any other host: worktree off its `branch`, update, full apply, commit, push, PR. No other host is started while the canary is in flight. If the canary yields no update PR for any reason (worktree refused, nothing to commit, push or PR failure), its result is `fail`: halt and report why. Never move on to `rest` without a canary PR whose required checks passed.
91:3. **Record the canary's push timing** — before removing its worktree (step 3's cleanup). Read the newest `.lisa/push-timing/*.json` report in the canary worktree (written by the pre-push timing report, CodySwannGT/lisa#4591) and keep its `startedAt` and `wallMs`. If the directory is absent or empty, record `push timing: not recorded (no .lisa/push-timing report in the canary worktree)` — do not estimate one.
92:4. **Wait for the canary PR's required checks** with a bounded, foreground, blocking watch, all within one 540-second budget. Never start a detached or background watcher, and never poll in an open-ended loop.
93:   - First, poll `gh pr checks <canary-pr> --required --json name` (every 30 seconds, inside the same 540-second budget) until at least one required check is registered — checks can take a moment to appear after the push. If none ever appears, the result is `fail` with the reason `no required checks reported` (report that reason, not an empty list of failing checks): nothing proved the release is safe.
97:   timeout "$remaining" gh pr checks <canary-pr> --required --watch --interval 30 --fail-fast
100:   Run it in the foreground with the tool's own command timeout set to at least 600000 ms, so the command's exit code actually arrives; a command the harness kills (no exit code) counts as `timeout`. (`timeout` is GNU coreutils; on macOS use `gtimeout` from Homebrew coreutils. If neither exists, use `perl -e 'alarm shift; exec @ARGV or die "exec failed: $!\n"' "$remaining" gh pr checks …`, whose expiry exits 142; the `or die` keeps a failed exec from exiting 0 and reading as a pass.) Map the exit status to a canary result: `0` → `pass`; `124` (or `142` under the perl fallback) → `timeout`; any other non-zero → `fail`. On `fail`, collect the failing check names with `gh pr checks <canary-pr> --required --json name,bucket --jq '.[] | select(.bucket == "fail" or .bucket == "cancel") | .name'`.
104:   node scripts/lisa-update-projects-plan.mjs decide --canary-result <pass|fail|timeout>
108:6. **On `halt`:** touch no other host — no worktree, no install, no PR for anything in `rest`. Skip step 16 for the rest and **skip step 17** (Lisa's self-upgrade). Leave the canary PR open as it is for the human to judge; do not auto-fix it in this run (a failing canary is the signal that this release may be bad — rolling it back is a separate, deliberate act). Go straight to the [Report](#report).
109:7. **On `proceed`:** run steps 2–15 for every host in `rest`, each with its own `branch` from the plan. For this phase, use up to 4 parallel subagents to accomplish those steps (the apply itself still runs serially, per step 6). Then run step 16 for every open update PR (the canary's included), then step 17, then the Report.
115:The report always opens with a **Canary** section:
117:- **Host:** the canary's local path and target branch.
118:- **PR:** the canary update PR's URL.
120:- **Push timing:** the `startedAt` and `wallMs` from the canary's push-timing report, or `not recorded (no .lisa/push-timing report in the canary worktree)`.
122:If the plan script refused, the Canary section reads `not designated`, followed by the plan script's message and the line `no host was touched`.
124:Then a **Rest** section: on `proceed`, one line per host with its PR URL and merge state (or why it was skipped, per step 4); on `halt`, the line `halted by the canary — no other host was touched, Lisa's self-upgrade was skipped` followed by the hosts that were not updated. Finally, the **Lisa self-upgrade** outcome (PR URL, "no pending changes", or "skipped: canary halted").
