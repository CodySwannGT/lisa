Upload text evidence to the configured GitHub evidence release (default pr-assets), update PR description, post JIRA comment with code blocks, and move ticket to the configured review status only when `jira.workflow.review` is set (otherwise leave it in `claimed`). Reusable by any skill that captures evidence and generates evidence/comment.txt + evidence/comment.md.


# JIRA Evidence Posting

## Workflow resolution

The post-build review status is read from `.lisa.config.json` `jira.workflow.review` (or `jira.workflow.code_review`). `review` is optional; when unset, the ticket stays in `claimed` until `done` and this skill skips the transition. Never transition to a status that is not named in `config.jira.workflow`. If the configured status is not a valid transition from the current state, log a warning and skip.

```bash
REVIEW=""
if [ -f .lisa.config.json ]; then
  _cfg=$(jq -r '.jira.workflow.review // .jira.workflow.code_review // empty' .lisa.config.json 2>/dev/null)
  [ -n "$_cfg" ] && REVIEW="$_cfg"
fi
if [ -f .lisa.config.local.json ]; then
  _local=$(jq -r '.jira.workflow.review // .jira.workflow.code_review // empty' .lisa.config.local.json 2>/dev/null)
  [ -n "$_local" ] && REVIEW="$_local"
fi
```


Upload captured evidence and generated templates to GitHub PR description and JIRA ticket. This skill is the posting step — it assumes evidence files and comment templates already exist in the evidence directory.

## Arguments

`$ARGUMENTS`: `<TICKET_ID> <EVIDENCE_DIR> <PR_NUMBER>`

- `TICKET_ID` (required): JIRA ticket key (e.g., `PROJ-123`)
- `EVIDENCE_DIR` (required): Directory containing evidence and templates (e.g., `./evidence`)
- `PR_NUMBER` (required): GitHub PR number to update description

## Prerequisites

- `python3` for destination validation. Configure `server` as a bare HTTPS origin:
  no userinfo, path prefix, query, or fragment. Invalid destinations are rejected
  before Basic authorization is constructed.
- `JIRA_API_TOKEN` environment variable set
- a jira-cli config — `.lisa/jira-cli/.config.yml` if the `setup-jira-cli`
  SessionStart hook wrote one, otherwise `~/.config/.jira/.config.yml`. `server`
  and `login` are read from whichever is used, and the fallback is announced on
  stderr rather than taken silently.
- `gh` CLI authenticated
- Evidence directory containing:
  - `NN-name.txt` or `NN-name.json` text evidence files (e.g., `01-health-check.json`)
  - `comment.txt` — JIRA wiki markup (generated by `generate-templates.py`)
  - `comment.md` — GitHub markdown (generated by `generate-templates.py`)

## Comment-body preflight (required)

Before posting or updating anything, check the evidence body (`comment.md`, and `comment.txt` where this skill uses it):

- It contains a `## Not established` heading. That heading is **never omitted and never blank** — when nothing is outstanding it still renders `None outstanding — reviewed`; otherwise it names, in plain operator language, what the verification did not prove.
- The accompanying verdict carries `not_established_reviewed: true` (the list may be empty; the flag may never be omitted).
- It contains a `## Artifact identity` heading carrying **values, not placeholders** — the repository, the `head_sha` the verification observed, the `environment`, and per artifact its `sha256` digest and `captured_at`. **Refuse to post** a body whose identity heading is absent or unpopulated, or whose recorded `artifact_head_sha` disagrees with the verdict's `artifact.head_sha` — report the evidence id and **both SHAs**. Definition: the `claim-evidence-mapping` rule.

If either is missing, **refuse to post**: stop and report the missing Not-established review to the caller instead of publishing. Composing the body is `lisa-tracker-evidence`'s job (see its UI Evidence Checklist); this skill only refuses to publish one that omits the section. The section is defined by the `claim-evidence-mapping` rule and generalizes `lisa-improve-harness`'s required, never-empty `Known limits` field.

## Usage

Resolve the evidence release once, before posting. When `generate-templates.py` wrote the evidence links, use the same release it used so the links match the uploads. If the release cannot be used (for example, it is nearly full), the step prints `Evidence release not usable; stop.` and fails: stop there and report it instead of posting.

If you came here from jira-journey, `generate-templates.py` already wrote the links: skip the block below and reuse the release name jira-journey printed in its Step 4, because resolving again can pick a different month's release.

```bash
unset LISA_EVIDENCE_RELEASE; LISA_EVIDENCE_RELEASE=$(node scripts/lisa-work-item.mjs evidence-release --ensure) || { echo "Evidence release not usable; stop."; false; } &&
export LISA_EVIDENCE_RELEASE && echo "Evidence release: $LISA_EVIDENCE_RELEASE"
```

Some agent runtimes start a new shell for every command, and a new shell forgets an exported value. So put the printed release name in front of every later command that reads it, as `LISA_EVIDENCE_RELEASE=<name>`; the commands below show where.

```bash
LISA_EVIDENCE_RELEASE=<name> bash .claude/skills/jira-evidence/scripts/post-evidence.sh <TICKET_ID> <EVIDENCE_DIR> <PR_NUMBER>
```

### Example

```bash
LISA_EVIDENCE_RELEASE=pr-assets bash .claude/skills/jira-evidence/scripts/post-evidence.sh PROJ-123 ./evidence 42
```

`post-evidence.sh` uses `LISA_EVIDENCE_RELEASE` when it is set, after the resolver confirms it is one of the project's evidence releases and is not nearly full. A pinned release is an exact choice and never rolls over; without a pin, a nearly full release rolls over to its next overflow release (`<release>-2`, `-3`, …).

## What It Does

1. **Read JIRA config** — Resolves the jira-cli config (`$PROJECT_DIR/.lisa/jira-cli/.config.yml` first, then `~/.config/.jira/.config.yml`, announcing the fallback) and reads `server` and `login` from it dynamically — no hardcoded values. Exits 1 naming both paths when neither exists. The same resolved path is then passed to `jira issue move` as `--config`, so the CLI cannot end up on a different config than the one this script parsed.
2. **Upload to the configured evidence release (`node scripts/lisa-work-item.mjs evidence-release --ensure` prints it; default `pr-assets`)** — Validates `PR_NUMBER` as a positive integer, uploads each evidence file as `pr-<PR_NUMBER>-<file>` via `gh release upload --clobber`, then lists the release and exits 1 naming any uploaded asset that is missing. Before uploading it refuses an evidence name outside `NN-name.(png|txt|json)` with letters, digits, `.`, `_` and `-` only (GitHub rewrites other characters in asset names), and before editing the description it exits 1 naming any Markdown link or image target in `comment.md` (inline, titled, `<url>`-bracketed or a reference definition such as `[ref]: url`) that points into that release but is not `pr-<PR_NUMBER>-…` or was not uploaded by this run (a stale asset from an earlier run does not count; release URLs quoted as plain text in inlined evidence are ignored). `--clobber` therefore only ever replaces this pull request's own earlier upload.
3. **Update PR description** — Replaces or appends the `## Evidence` section in the PR body
4. **Post JIRA comment** — Posts `comment.txt` as a new comment (wiki markup with code blocks)
5. **Move ticket to the configured review status** — Transitions the JIRA ticket to `$REVIEW` (default: `Code Review`).

## Evidence Naming Convention

Text evidence files are named: `{NN}-{evidence-name}.txt` or `{NN}-{evidence-name}.json`

```text
evidence/
  01-health-check.json          uploaded
  02-schema-after-migration.txt uploaded
  03-rate-limit-response.txt    uploaded
  comment.txt                   used for JIRA comment
  comment.md                    used for PR description
```

Local evidence files keep their `NN-` names. In the shared evidence release each one is stored as `pr-<number>-<file>` (for PR 42, `01-health-check.json` becomes `pr-42-01-health-check.json`), so two pull requests with a same-named file never overwrite each other's evidence. `generate-templates.py` links that scoped name.

## Troubleshooting

### Evidence not appearing in GitHub PR

Evidence files must be in the configured evidence release (`node scripts/lisa-work-item.mjs evidence-release --ensure` prints it; default `pr-assets`). It creates the release when it is missing and, when it is nearly full, rolls over to the next overflow release (`<release>-2`, `-3`, …) and prints that one:

```bash
node scripts/lisa-work-item.mjs evidence-release --ensure
```

It refuses only when a pinned `LISA_EVIDENCE_RELEASE` is full (unset it, or pin
a release with room) or every overflow release of the period is full (set
`verification.completion.evidenceRelease` in `.lisa.config.json` to a rotating
name such as `pr-assets-{YYYY-MM}`, or prune old evidence); older evidence keeps
validating.

### JIRA API returns 403

Ensure `JIRA_API_TOKEN` is set and `login` in the resolved jira-cli config (`.lisa/jira-cli/.config.yml`, else `~/.config/.jira/.config.yml`) matches your Atlassian account email.
